TD-025Should the app normalise a base URL that already ends in `/v1`? Both answers are defensible and the product has deliberately picked neither**Both branches are reasonable, which is exactly why this may not be settled in passing.** Never rewriting is defensible because the URL is the user's own, and a gateway that wants `/v1` inside its own base is misconfigured against `ServiceEndpoint`'s contract — rewriting it would paper over a real misconfiguration. Stripping is defensible because OpenAI-compatible gateways overwhelmingly serve `{root}/v1/...` while the value a user has to hand is the one printed in the README, so "never rewrite" makes the most common paste on the internet fail quietly. The cost of stripping is that it silently changes the request target and would break a real, if rare, service that genuinely lives at `{root}/v1/v1/...`. The decision belongs to a human specifically because it changes what the app does with a value the user typed; a fix round whose scope was copy and gates is the wrong place to answer it, and a behaviour change hidden inside a copy fix is the worst available outcome.
TD-028A superseded API key stays in `ServiceConnections` forever, and the product has deliberately picked neither "keep it" nor "erase it"**Both branches are reasonable, which is why this may not be settled in passing.** Erasing superseded keys is defensible because what is retained is not an audit record but a live secret: a key the user rotated away from, or revoked at the provider, sits in a SQLite file in plaintext with no UI, no expiry and no way to tell it is dead — and a local-database app whose whole credential story is "paste a key" makes the residue a liability the user was never shown. Retaining them is defensible because it is the only record of what the app was configured against: `SaveConnectionHandler` reuses the active row to carry forward `Variant`, `MaxTokens` and `Temperature`, a reconnect after a bad paste should be recoverable, and an audit trail of which endpoint a request went to is exactly what a settings page ought to keep. The cost of each is symmetric and neither is free. Erasing loses the history and breaks any future "what did I have set up last week" or "which base URL failed" debugging, and it must happen at the write choke (`SaveConnectionHandler`, where the demotion already is) or the retention will reappear through another insert path. Retaining means the credential footprint grows with every save, unbounded and invisible, while the page reports "not connected". The decision belongs to a human specifically because it is a product promise about stored secrets rather than a refactor; this pass corrected the copy that misstated it, and a behaviour change hidden inside a copy fix would be the worst available outcome. The same shape as TD-025, and deliberately the same treatment: registered, not decided.

TD-029The metrics ledger has no home for work that revisits an already-shipped shardThe factory's central measurement claim is "measure touch, not time" per shipped shard. Today the state is an accident of schema growth, not a decision.
